## 1 引言

### 1.1 编写目的

本文档是E方向"监管驾驶舱"的需求基线文件，供三类读者使用：①组内开发/测试作为功能实现与用例设计的依据；②评审教师作为需求答辩与冻结基线的评审对象；③互审小组（结对交叉测试组）作为执行测试的输入。文档通过答辩后冻结为V1.0，此后任何需求改动须经第8章变更流程。

### 1.2 项目背景

餐饮业油烟监控平台1.0（Jeecg-Boot单体架构：Spring Boot 2.7.18/JDK21/MySQL/Redis + Vue2/Ant Design Vue）已实现在线监控、智能预警、档案与报表，但数据分散在各报表页，监管者"看得见数据、看不见态势"。本组认领E方向"监管驾驶舱"，为局领导与值班人员提供区域一屏总览（地图热力、实时告警、企业信用红黄绿牌、多维统计），并作为2.0六组成果的统一展示出口——A组预测榜单、C组自查整改、D组处置数据最终汇入本大屏，使平台从"只监控"升级为"监控+决策"。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 驾驶舱/大屏 | 1920×1080深色风格的全屏监管可视化页面 |
| 红黄绿牌 | 企业信用等级：红<60≤黄<80≤绿（阈值可配置，百分制） |
| 评价周期 | 信用计算的时间窗（默认自然月，可配置） |
| 聚合接口 | 将大屏五区数据合并为一次返回的服务端接口（/v2/dashboard/aggregate） |
| 峰谷轮询 | 峰时30s~1min、谷时≤5min的自适应前端轮询策略 |
| 口径 | 统计指标的分子/分母/时间窗定义，须与1.0报表一致 |
| 热力权重 | 地图热力值=近30天超标频次×浓度归一化 |
| MUST/SHOULD/COULD | 功能三级优先级：验收底线/应当实现/可选加分 |

### 1.4 参考资料

《软件工程技术综合实践方案》（E方向功能边界4.6节）；《实践指导书》任务1~3；《指导讲义（2026）》；1.0源码（psms/home、analyse、supervision三包统计接口，见《执行方案》附录B）；《跨组接口契约清单》（03号文件）；ECharts 5 与 vue-baidu-map 官方文档；GB 18483《饮食业油烟排放标准》。

## 2 总体描述

### 2.1 系统目标与范围（MVP边界）

**MUST（验收底线）**：区域总览地图（点位+超标热力）→实时告警滚动→企业信用红黄绿牌（规则可配置、结果可公示）→多维统计图表（告警趋势/行业分布/处理率）→大屏整体布局（1920×1080深色、刷新≤5分钟）。构成"一屏看态势"最小闭环。

**SHOULD**：大屏轮播模式；信用规则配置页（管理员在线维护指标与权重）。

**COULD（加分项）**：大屏AI周报摘要（大模型生成，降级可用）。

**明确不做（范围外）**：①不重写1.0已有统计（复用改造22个现成接口）；②不做预测模型本体（消费A组结果）；③不做移动端大屏（企业侧小程序属C组）；④不做告警处置流程（预警处理属1.0/监管侧已有）；⑤不做工单业务本体（仅可能消费D组时效统计，W3裁决）。

### 2.2 用户角色

| 角色 | 说明 | 使用端 | 高频场景 |
|---|---|---|---|
| 局领导 | 区生态环境局领导，监管决策者 | 大屏（只读） | 周期性查看全区态势、红牌企业督查调度 |
| 值班人员 | 监控值守员，8小时在岗 | 大屏（只读） | 盯实时告警滚动、异常区域定位 |
| 系统管理员 | 平台管理员（1.0 admin体系） | Web管理端 | 维护信用规则、发布/下架信用公示 |
| 餐饮企业负责人 | 被监管对象（只读公示结果） | Web公示页 | 查看本企业信用等级与扣分明细 |

**非人员参与者**：信用评价定时任务（Quartz）；前端轮询服务（聚合接口消费方）；上游数据服务（A组预测榜单、C组自查整改统计）；大模型API（AI周报，COULD）。

### 2.3 运行环境与约束

沿用1.0技术栈与2026基线：JDK 21/Spring Boot 2.7.18/MySQL 8（psms库）/Redis/Node 22或24；前端 Vue2 + Ant Design Vue 1.7 + ECharts 5.2.1 + vue-baidu-map 0.21.22。约束：①新模块以增量方式集成，**不得修改1.0既有表结构**；②界面风格遵循《E组工程与界面风格基线》（管理页100%沿用1.0三段式、大屏深色但品牌同源）；③六组代码合并dev主干打v2.0.0-release标签；④接口前缀 /v2/dashboard、/v2/credit、/v2/stat，错误码25xx段；⑤大屏刷新周期MUST≤5分钟。

## 3 业务流程与用例模型

### 3.1 核心业务流程（文字版，正式稿替换为draw.io图）

**流程A 信用评价主流程**：管理员维护规则（UC-E04）→定时任务按周期触发计算（UC-E08）→引擎拉取输入（1.0告警/超标统计＋C组自查整改统计）→按规则加减分写入明细（bu_credit_detail）→汇总评级红/黄/绿（bu_credit_record）→管理员发布公示（UC-E05）→大屏信用榜与公示页更新（UC-E03）→（闭环）企业按扣分项整改→下周期分数回升。

**流程B 值班监控主流程**：值班员打开大屏（UC-E01）→前端轮询拉取聚合数据（UC-E09）→新告警滚入告警区（UC-E02）→点击地图热力异常区域定位→查看趋势/行业分布佐证（UC-E06）→通知网格员现场核查。

**流程C 周报摘要（COULD）**：每周一定时汇总上周统计JSON→调用大模型生成结构化周报→超时/非法输出降级为纯统计数字并标识"降级模式"。

### 3.2 总体用例图（文字版，正式稿替换为PlantUML图）

参与者四类（局领导、值班人员、系统管理员、餐饮企业负责人）+非人员三类（定时任务、前端轮询、上游数据服务）。用例10个及关系：UC-E04 —include→ 规则校验；UC-E08 —include→ UC-E04的规则集读取，—extend→ C组数据不可用时降级计算；UC-E03 —extend→ 点击企业查看扣分明细；UC-E01 —include→ UC-E09（聚合拉取）；UC-E10 —extend→ UC-E06（周报引用图表数据）。用例总量10个（满足8~15要求）。

### 3.3 用例规约

> 核心规约详写3个（UC-E01/03/04，七字段+每用例≥2异常流）；其余7个以简表收口。执笔人见各规约尾注。

**UC-E01 查看区域总览地图（核心规约）**

| 字段 | 内容 |
|---|---|
| 参与者 | 局领导、值班人员 |
| 前置条件 | 用户已登录且有dashboard:screen:view权限；区域内存在已接入监测点 |
| 基本流 | 1 用户进入大屏；2 系统按峰谷策略拉取聚合数据（UC-E09）；3 地图渲染监测点点位（坐标取base_company.lng/lat）；4 按"近30天超标频次×浓度归一化"渲染热力图层；5 用户缩放/点击点位，查看企业名称与最新浓度；6 数据按刷新周期自动更新 |
| 扩展流 | 3a 点位坐标缺失（企业未填经纬度）：该点位不渲染并在数据质量面板计数提示，不影响其余点位；4a 热力数据为空（近30天无超标）：显示"无超标热力"轻提示，底图与点位正常；2a 聚合接口超时（>3s）：展示缓存值+「降级模式」角标，自动重试 |
| 后置条件 | 大屏地图区展示完整态势；本次拉取计入缓存命中统计 |
| 业务规则 | 热力权重口径与1.0超标统计一致（statPointExcessive口径，见《口径对齐清单》KD-02）；地图底座为百度地图；区域过滤遵循1.0 fidRegion数据权限 |

**UC-E03 查看企业信用榜单（核心规约）**

| 字段 | 内容 |
|---|---|
| 参与者 | 局领导、值班人员（大屏）；监管人员（Web公示页） |
| 前置条件 | 当前评价周期已执行计算（UC-E08）且结果未过期 |
| 基本流 | 1 用户查看大屏信用区；2 系统按当前周期读取bu_credit_record；3 按总分升序输出榜单（红牌优先），展示红/黄/绿牌色与企业名；4 用户点击某企业；5 展示该企业得分、等级与扣分明细（bu_credit_detail逐条，含触发依据单号） |
| 扩展流 | 2a 当前周期未计算：显示上一周期结果并标注"截至××周期"；4a 企业无明细（满分公司）：提示"本周期无扣分记录"；5a 记录数>50：分页加载 |
| 后置条件 | 榜单展示与库内record一致；点击行为计入浏览日志（@AutoLog） |
| 业务规则 | 等级阈值红<60≤黄<80≤绿（阈值配置于规则表，可调）；同分并列按企业名称排序；榜单只读，修改只能走UC-E04改规则后重算 |

**UC-E04 维护信用评价规则（核心规约）**

| 字段 | 内容 |
|---|---|
| 参与者 | 系统管理员 |
| 前置条件 | 已登录且持有 credit:rule:edit 权限 |
| 基本流 | 1 管理员进入规则配置页（1.0三段式：搜索区+表格+弹窗表单）；2 新增/编辑规则：填写指标代码、名称、类型（加分/减分，字典）、分值、权重、评价周期类型；3 系统校验唯一性与数值合法性；4 保存入库（bu_credit_rule）；5 规则在下一次评价计算时生效 |
| 扩展流 | 3a 指标代码重复：提示并阻止保存（错误码25001规则已存在）；3b 分值/权重非法（负数、超上限）：字段级红字提示；2a 无权限用户尝试进入：菜单隐藏+接口返回403；5a 规则停用：历史计算结果不受影响（快照不回溯） |
| 后置条件 | 规则变更留审计（create_by/update_by）；变更后下一周期计算使用新规则 |
| 业务规则 | 规则数量≥1且至少含一条减分项方可发起计算；同一指标代码全局唯一；生效规则集整体快照存入当期record |

## 4 功能需求条目（FR-E01~E10）

> 验收标准按Given-When-Then；优先级沿用MUST/SHOULD/COULD；与用例对应关系见第7章追溯矩阵。

| 编号 | 名称 | 优先级 | 需求描述 | 验收标准（G-W-T） |
|---|---|---|---|---|
| FR-E01 | 区域总览地图 | MUST | 监测点点位展示+超标热力图（百度地图底座，坐标取企业经纬度） | Given 区域内≥1个在线监测点 When 大屏加载完成 Then 全部点位≤3s渲染且热力权重与KD-02口径一致 |
| FR-E02 | 实时告警滚动 | MUST | 最新告警按时间倒序滚动展示，新告警高亮 | Given 存在新告警 When 到达刷新周期 Then 新告警出现在列表首位于一个周期内且高亮 |
| FR-E03 | 企业信用红黄绿牌 | MUST | 按可配置规则周期性评价，输出等级榜单 | Given 企业周期得分80和79.99 When 计算完成 Then 前者为绿牌、后者为黄牌（边界正确）；榜单与bu_credit_record一致 |
| FR-E04 | 信用规则维护 | MUST(接口/数据层)/页面SHOULD | 规则在线增删改查、启停、按周期类型分类 | Given 无权限账号 When 调用规则编辑接口 Then 返回403；Given 重复指标代码 When 保存 Then 返回25001且不落库 |
| FR-E05 | 信用结果公示 | MUST | 评价结果发布/下架公示，企业可查本人等级与明细 | Given 周期未发布 When 查询公示 Then 返回25003；Given 已发布 When 企业登录 Then 可见本人等级与扣分明细 |
| FR-E06 | 多维统计图表 | MUST | 告警趋势（7日）、行业分布、处理率图表 | Given 任一图表数字 When 与1.0对应报表核对 Then 与《口径对齐清单》逐项一致 |
| FR-E07 | 大屏轮播模式 | SHOULD | 大屏分区/整页轮播，可开关、间隔可配 | Given 开启轮播间隔30s When 到时 Then 自动切换且请求不泄漏 |
| FR-E08 | 信用评价周期计算 | MUST | Quartz按周期自动执行，输入含1.0统计与C组数据 | Given C组接口不可用 When 本期计算 Then 跳过该项、明细备注"数据源缺失"、其余规则正常计分 |
| FR-E09 | 大屏聚合数据接口 | MUST | 五区数据一次返回，峰谷缓存，分区降级 | Given 某分区数据源失败 When 请求聚合接口 Then 该分区null+degraded:true且HTTP 200、其余分区正常 |
| FR-E10 | 大屏AI周报摘要 | COULD | 周期统计JSON→大模型→结构化周报 | Given 大模型3s超时 When 请求周报 Then 返回纯统计降级版并标识"降级模式" |

## 5 非功能需求（逐条量化+架构落点）

| 类别 | 指标 | 架构落点 |
|---|---|---|
| 性能 | 聚合接口在模拟500监测点×7天数据下响应<500ms；刷新周期MUST≤5min、目标峰时30s~1min | 聚合接口+请求合并+Redis缓存 |

| 可维护性 | 信用规则/轮播间隔/峰谷参数全部配置化，调整不改代码 | bu_credit_rule+1.0系统参数 |

## 6 数据需求

**新增数据实体（3张，遵循指导书表规范：bu_前缀/id varchar(36)/create_by等审计字段/del_flag/状态挂字典，DDL由李晓倩另行交付入db/v2_upgrade.sql）**：

| 实体 | 关键字段 | 与1.0表的关联 |
|---|---|---|
| bu_credit_rule 信用评价指标 | rule_code(唯一)、rule_name、score_type(字典：加分/减分)、score_value、weight、cycle_type(字典)、enabled(字典) | 独立配置表，无外键 |
| bu_credit_record 评价结果 | company_id、cycle、total_score、level(字典：红/黄/绿)、snapshot(JSON规则快照)、publish_status(字典) | 逻辑外键 company_id→base_company.id（冗余存企业名） |
| bu_credit_detail 变动明细 | record_id、rule_id、change_score、source_no(触发依据：告警id/整改单号)、remark | record_id→bu_credit_record.id；rule_id→bu_credit_rule.id |

**沿用的1.0核心表**：base_company（企业名/经纬度lng,lat/经营类别business_category/区域area_code）、base_point（点位/point_mac设备标识/status）、bu_lampblack_data（油烟浓度与风机净化器状态，含_now/_today/区域动态分表，yyyymmdd日期键）、base_point_log（开关机日志，**注意：不在psms.sql中，部署需补建**）、bu_purifier_powerdata（净化器工况）。**不修改任何1.0表结构**；跨组消费数据（A组榜单、C组自查统计）走接口不落E组新表，仅在明细source_no中记录来源单号。
